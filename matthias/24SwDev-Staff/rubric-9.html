In plain OO terms, but mostly applicable to FP:

The first batch of inspections concerns Bazaar/Server/player:

  • Bazaar/Server/player must implement the same interface as Bazaar/Player/mechanism, that is, accepting

    • 10 points for name calls and return the name sent by the client.

      There is no need for this call to go “over the wire” because the name is available when the proxy is created. See the remote protocol.

    • 10 points for setup calls, turn the arguments into JSON, get result ("void") in JSON, return void.

    • 10 points for requestPebbleortrades calls, turn them into JSON, receive a JSON response, return it as an internal value.

    • 10 points for requestCards calls, turn them into JSON, receive a JSON response, return it as an internal value.

    • 10 points for win calls, turn them into JSON, get result ("void") in JSON;

    Any method that receives a result from a remote site may decide to reject the JSON it receives because (1) it is ill-formatted or (2) invalid for a particular call. It may not try to check the rules on any internal value it constructs.

    The key is that no method does more (or less) than exactly that. Take off all pts if any of them do more or less.

  • 15 points for constructors (builders, factories) that receive handles for sending/receiving over some stream (so that TCP can be mocked);

  • 15 points for unit tests for Bazaar/Server/player

    Unit tests for the proxies may merely check that the object writes JSON for the given arguments to a mocked output stream and can receive

    See below for my code of how to set up mock tests.

The second batch of inspections is about Bazaar/Clients/referee:

  • Bazaar/Clients/referee must implement the same "context" as Bazaar/Player/referee, namely, receiving and making:

    • 10 points for setup calls

    • 10 points for requestPebbleortrades calls

    • 10 points for requestCards calls

    • 10 points for win calls

    Consider it a co-proxy. (There is a mathematical intuition behind this term.)

    The typical implementation should be a loop that reads a JSON expression from an input stream; transforms it into internal data representation (e.g., a setup call comes with a bunch of equations); performs the method call for the one specific player it controls (see below); and writes the result as JSON to the output stream (e.g., an action for one of the turn methods).

    Any method may decide to reject the JSON it receives because (1) it is ill-formatted or (2) invalid for a particular call. Here “reject” means shut down the entire client setup and inform its owner of the server’s bad behavior.

    No method should do more or less.

  • 15 points for constructor (builder, factory) must receive (1) a player and (2) handles for sending/receiving JSON over streams.

  • 15 points for unit tests for Bazaar/Client/referee

    Unit tests for the proxy player may just check whether the method can read JSON arguments from a mock input device. See above for a detailed descriptions and below for an example.

All of this applies to OOP and FP. If you find something incomprehensible for the latter, ask one of the instructors.

For the Clients-Server part, we merely spot-check two aspects, one per:

  • 20 points for synchronizing client start-ups with servers;

    That is, imagine someone starting the client before the server is up.

    The client must wait or shut down gracefully. Waiting is ideal. Graceful shut-down is acceptable. Crashing means a loss of all points.

    The key is to look for an exception-handling block that deals with a network connectivity failure around the place where the client connects and sends the name over. The handler may call for a retry for a certain number of times or shut down the client with an appropriate error message but not a stack trace print.

  • 20 points for abstracting over the “wait for two periods” property of the server.

    The server is specified to wait for two periods but “two periods” should not be hard-wired into the code.

    One way to hard-wire is to have two copies of the same wait-period code. It implies a loss of all points.

    Another one is to have a function that performs the waiting task and to call it twice. Take off half the points.

    The third one is to set up a loop in a wait-period function that has a hard-coded 2 in it, as in

        for(int i = 0; i < 2; i++)

          accept_players();

    Take off 5 points.

Design – everyone🔗

design: 35 points

For the first design task, the document should mention two items:

  • 5 points for a change to the data representation of the referee’s knowledge about players that includes the cards a player has purchased;

  • 5 points for a change to the rule book’s “determine winners and losers” functionality so that it can assign a bonus for the red-white-and-blue flag.

No other changes should be needed. Separating the rule-book change from the knowledge representation change is necessary because the two co-CEOs may come up with another way of computing a bonus for a collection of cards. In a sense, my request to study a second change to the game is a hint, which is why it is justified to grant these points on an all-or-nothing basis.

The second design task demands changes to several layers in the dependency graph:

  • 5 points for a change to the data representation of pebbles in any language;

  • 15 points for a potential change to the data representation of cards and wallets;

    In an untyped language, say Python, this may require a change to the representation of cards and wallets, because it is tempting to stick plain colors into those.

    In a typed language, say Java, this may work out if the data representation for pebbles already used an interface (against the recommendation of F II). If a Java-ish program used an enumeration, the change is pervasive in both.

  • 5 points for both of the changes above, with an additional note that the “determine winners and losers” functionality must check for colors and the glowing factor.

My Mock🔗

Here is a test scenario for my remote-proxy player:
(test-remote make-remote-player b
             (setup equations1)
             #:remote (void->jsexpr (void))
             #:exp    (void)
             #:msg   `["setup" [,json-of-equations1]])
It makes a particular (healthy) player with make-remote-player; checks that it sends a JSON message formatted like a method call (#:msg); and deals with the response (void) properly.

The code that sets up such mock tests is a compile-time function:
(define-syntax (test-remote stx)
  ; #:remote JSexpr ~~ what the client responds with
  ; #:exp JSexpr    ~~ what we expect the method to produce in response
  ; #:msg JSexpr    ~~ what the method sends to the client
  (syntax-parse stx
    [(_ make-remote-player name:id
        (method args ...)
        (~optional (~seq #:remote input) #:defaults ([input #'(~a "void")]))
        (~optional (~seq #:exp e) #:defaults ([e #'(void)]))
        #:msg m)
     #'(check-predicate ..
        .. (with-output-to-string ..
             (with-input-from-string (jsexpr->string input) ..)) ..)]))

See the (with-output-to-string ..) and (with-input-from-string (jsexpr->string input) ...) expressions to understand how easy a language should make it to set up mock streams.
