41.1 Design Choices🔗

Mixing typed and untyped code poses many design questions, and some are still being explored. Let’s consider the question of whether developers want to benefit from type safety:

  • check the types and then throw them away

  • compile types to instructions that ensure safe interaction between typed and untyped source pieces

41.2 Costs and Benefits🔗

- language implementer: almost no work for the type checker

- language implementer: serious work of adding appropriate checks to the machine

- IDEA: closed system could list all objects that have a given structural type

- ... and enforce it with a series of ‘is-a?‘ checks.

- NO: this reduces to transient and require compilation of typed code

- throwing types away allows the code to run at the same speed as the underlying untyped PL

- translating types into type checks assists sw devs with finding mistakes in "type veneers" - ... see DefinitelyTyped

45 A CESK Machine for a Mixed-Type Setting🔗

- represent type classes differently

- ‘new‘ of a typed class creates a typed _proxy_

- the CESK machine knows all equivalence classes of structural types

- ‘call‘ into a typed proxy checks each object argument for membership in equivalence class

- ‘setter‘ into a typed proxy checks an object for membership in equivalence class

- ‘get‘ does what? If get occurs in a typed context, do we need a ‘typed-get‘
