Why do languages support structured data and abstraction mechanisms?

28 The Pragmatics Question🔗

Can a developer avoid copying and pasting code? No.

Can a developer create a data representation for two-dimensional points?

Yes. A developer can combine two numbers into a single number and extract the two original ones. But, this kind of programming is complicated and error-prone. Without a way to introduce function-like abstractions of code, the encoding and decoding has to be repeated over and over again. Worse, when a piece of code processes a single number, it is impossible to check whether this number represents a two-dimensional point or just a plain number (say a distance).

28.1 Design Choices🔗

Language creators have always responded to both of these questions together. Over the decades, they have developed two different solutions to these questions:

  • classes, which combined several pieces of data via fields and allow abstraction over repeated, similar pieces of code via methods; and

  • functions—also known as procedures—and records—also known as structures—-which are separate answers to the two questions.

Over time, class-based object-oriented programming has dominated the landscape, though recently almost all widely known languages have combined the solutions.

We will study a model of the first approach:

  • classes with just fields and methods;

  • without constructor;

  • without encapsulation mechanisms (private fields or methods).

  • without inheritance and overriding.

28.2 Costs and Benefits🔗

- language implementer: syntax: well-formed & valid need revision

- language implementer: semantics: new instructions for CESK machine, plus a table of classes

- dev: avoids code repetition

- dev: improved representation of information (less encoding)

- dev: organizing data together with functionality

- dev: classes and dynamic dispatch introduce some complexity: a programmer must somehow figure out that calling a method on an object performs the proper actions
